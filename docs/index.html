Claude Counter Architecture

An overview of the execution flow, inter-script communication, and token tracking architecture.

1. Project Overview

Claude Counter is a browser extension designed to monitor and visualize token usage limits and contextual limits on Claude.ai.

Because Claude's frontend interacts heavily via React and fetches data primarily through Server-Sent Events (SSE) and XHR that don't emit native events easily interceptable by traditional content scripts, this extension implements a dual-layer approach. It injects code directly into the webpage's context to hook into network requests and push those events back to a securely isolated extension content script for tracking.

2. System Architecture

The system comprises three primary execution contexts due to browser security boundaries. Communication between them is orchestrated through event listeners and custom `postMessage` RPC architectures.

3. Core Modules Breakdown

src/content/main.js

The core orchestrator. Bootstraps the application, hooks up `ui.js` listeners, injects the bridge, processes usage and SSE data limits, and handles URL navigation events using `MutationObserver` to ensure elements exist.

src/content/ui.js

Handles dynamic DOM manipulation and charting. Creates the header toolbars, settings overlay widgets, token percentage mini-bars, and message badges. Contains robust fallback logic for re-attaching UI elements when the React DOM aggressively resets.

src/content/tokens.js

Handles evaluating conversation histories. Uses the loaded OpenAI/Anthropic tokenizers (`o200k_base.js`) locally to measure payload size and calculate specific breakdowns of tool use vs exact input strings in the current context.

src/content/bridge-client.js

A structured Promise-based RPC client inside the locked-down content world. Issues deterministic requests (like fetching a specific conversation history tree) to `bridge.js` while maintaining a pending queue with timeouts.

src/injected/bridge.js

Runs directly within the Claude.ai global object (`window`). It wraps `window.fetch`, `history.pushState`, and `history.replaceState`. This captures raw Event Streams for LLM generations directly observing Time-To-First-Token (TTFT) and data packets before React swallows them.

src/background.js

A minimal Service Worker. Responsible only for dispatching system-level push notifications to the OS using `chrome.notifications` when a usage threshold (like 80% or 95%) is breached, and handling keyboard shortcuts.

4. Network & Data Pipeline

The magic of the application lies in how it transparently captures conversational API payloads directly from memory rather than polling the DOM, preventing performance bottlenecks.

  • Network Interception: `bridge.js` monkey-patches `window.fetch`. When a POST to `/completion` originates, it fires a `cc:generation_start` event to signal to the UI that a request is pending.
  • Stream Buffering: The fetch hook clones the response body and attaches a `TextDecoder` to iterate over the `event-stream` chunks asynchronously, specifically listening for `message_limit` updates without interrupting the actual website's frontend.
  • Communication: Events and parsed JSON are dispatched back through `window.postMessage({ cc: 'ClaudeCounter', type, payload }, '*')`.
  • Processing: `bridge-client.js` inside the Content Script securely ingests this, filtering out anything untouched by the CC_MARKER. The data is passed to `main.js`, evaluated for tokens using `tokens.js` (including pruning the conversational tree trunk down to the exact thread branch), and the changes are applied natively via `ui.js`.

5. UI Injection Strategies

Modern SPAs tear down and rebuild DOM trees aggressively, making static element injections unreliable. To handle this, `claude-counter` utilizes `MutationObserver` heavily.

// main.js - Defensive Element Waiter
function waitForElement(selector, timeoutMs) {
    return new Promise((resolve) => {
        const existing = document.querySelector(selector);
        if (existing) return resolve(existing);

        const observer = new MutationObserver(() => {
            const el = document.querySelector(selector);
            if (el) {
                observer.disconnect();
                resolve(el);
            }
        });
        
        observer.observe(document.body, { childList: true, subtree: true });
    });
}

Using this logic, the app waits optimally until precisely when React renders the layout anchors (`MODEL_SELECTOR_DROPDOWN` or `CHAT_MENU_TRIGGER`), appending its UI elements adjacently to look indistinguishable from native design components.

6. Tools & Technology Stack

Vanilla JavaScript (ES6+)

The entire extension logic, UI manipulation, and event handling is built entirely without frontend frameworks like React or Vue to maintain maximum performance and the smallest possible bundle footprint.

Chrome Extension APIs (MV3)

Utilizes Manifest V3 architecture. Includes background service workers (`chrome.runtime`), local storage (`chrome.storage.local`), and native system notifications (`chrome.notifications`).

o200k_base Tokenizer

Local loading of the official tokenizer script (`vendor/o200k_base.js`) ensures identical token measurements to the actual Claude backend natively in the browser without external API calls.

MutationObserver API

Crucial for detecting layout shifts within Claude's React application to orchestrate UI lifecycle hooks when elements inevitably unmount and remount.

7. System Design Walkthrough

The system design revolves around Non-blocking Payload Intelligence. Unlike legacy extensions that scrape the DOM—which forces layouts to recalculate and slows down users—this system proxies network calls.

Data Aggregation Pipeline

  • Event Generation: The injected proxy monitors the network buffer and identifies requests to the `/completion` and `/chat_conversations` endpoints natively.
  • Stream Decoupling: Streams attached to `window.fetch` are safely cloned (`response.clone()`) and piped through a `TextDecoder` that evaluates SSE (`text/event-stream`) streams as they download into the RAM.
  • Tokenization Offload: Context counting natively supports "trunk pruning" (navigating structural parents up to ROOT IDs) so that branching conversations don't exponentially compound memory buffers. Tokens are physically counted on the client device saving infrastructure costs.
